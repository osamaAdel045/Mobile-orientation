      ### Android — Same as Native Android

      On Android, KMP shared code compiles to JVM bytecode through the standard
      Kotlin/JVM compiler. The DEX output is identical to an Android app written
      in Kotlin without KMP. There is zero overhead from KMP on Android — the
      shared module IS a native Android library.

      ```yaml
      KMP Android:  Kotlin → JVM Bytecode → DEX → ART
      Native Android: Kotlin → JVM Bytecode → DEX → ART
      Same pipeline. Same performance.
      ```

      ### iOS — Kotlin/Native ARM64

      On iOS, KMP shared code compiles to ARM64 machine code through LLVM — the
      same compiler back-end that Swift uses. The output is a standard Apple
      framework. For most business logic (networking, data processing, state
      management), Kotlin/Native performance is comparable to Swift.

      ```yaml
      KMP iOS:  Kotlin → LLVM IR → ARM64 → .xcframework
      Swift iOS: Swift → LLVM IR → ARM64 → .app
      Same back-end. Comparable code generation.
      ```

      ### Kotlin/Native Performance Characteristics

      Some differences exist between Kotlin/Native and Swift-native code:

      ```kotlin

      // 1. Primitive boxing — generics box primitives
      val list = listOf(1, 2, 3)  // List<Integer> — boxed on Native

      // 2. Garbage collection — tracing GC vs Swift ARC
      // Small allocations are comparable; large object graphs may differ

      // 3. String handling — Kotlin String vs NSString interop costs
      // Heavy string processing is faster in pure Kotlin/Native than bridged
      ```

      ### Coroutine Overhead

      ```kotlin
      // commonMain — coroutine overhead is minimal
      // A coroutine launch allocates ~160 bytes on JVM, similar on Native
      class AnalyticsTracker(private val scope: CoroutineScope) {
          fun trackEvent(name: String) {
              // Launching a coroutine per event is fine for typical usage
              scope.launch {
                  httpClient.post("/analytics") {
                      setBody(AnalyticsEvent(name))
                  }
              }
          }
      }
      ```

      <Callout title="GC on Kotlin/Native vs Swift ARC">
        Kotlin/Native uses a tracing garbage collector (since Kotlin 1.7.20).
        Swift uses Automatic Reference Counting (ARC). Both manage memory, but
        differently: ARC has deterministic release at the cost of retain cycle
        management; GC has non-deterministic release but no cycle problems. For
        mobile UI code (which is mostly on the platform side), the GC impact
        is minimal because platform objects are managed by the native runtime.
        Hot-path shared code should minimize allocations if GC pauses become
        measurable — typically only in rendering or audio code.
      </Callout>

      ### Compose Multiplatform Performance

      Compose Multiplatform on iOS renders through Skia — the same rendering
      engine as Flutter. Performance characteristics are comparable to Flutter:
      smooth 60fps rendering for most UI, with Skia's GPU-accelerated pipeline.
      The overhead comes from the Compose runtime (recompositions, diffing) rather
      than the rendering layer itself.

      ```yaml
      Compose MP iOS: Kotlin → Compose Framework → Skia → Metal → Display
      Flutter iOS:    Dart → Flutter Framework → Skia → Metal → Display
      Both run through Skia. Performance is comparable.
      ```

      ### KMP Insight

      KMP's performance profile is fundamentally different from Flutter or RN
      because KMP has no rendering engine. The shared module produces data — it
      does not produce UI. Performance comparisons should focus on business logic
      throughput, not frame rates. KMP matches native performance for logic because
      it IS native code on each platform.
