    ### How Gemini Contextualizes Your Project

    Gemini indexes build.gradle.kts dependencies to infer which DI framework, networking library, and database solution you use. When you request a ViewModel, it generates one using your project's Hilt or Koin setup rather than a generic template.

    <Callout title="AI-Generated Code Requires Active Validation">
        Gemini frequently suggests deprecated APIs from training data predating the latest platform releases. It cannot distinguish an API available since API 26 from one removed in API 34. Always verify imports against official docs, run lint, and test on your minimum SDK. Never assume correctness from syntactical validity alone.

    ### Test Scaffolding

    Gemini produces unit test skeletons using your project's testing libraries — MockK, Robolectric, or Compose UI Test — with approximately 70% first-pass accuracy. Always verify mocking logic and edge cases manually.

    ### Critical Limitations Specific to Android

    API fragmentation creates unique issues for AI generation. Training data may reference API 26-30 solutions while your minimum SDK is 33, surfacing `AsyncTask`, deprecated `Handler` usage, or pre-Compose lifecycle patterns. The model lacks awareness of device-specific capabilities — foldable displays, stylus input, and automotive SDK extensions require human expertise. Cross-platform AI tools generate generic widget code that ignores Android-specific accessibility and hardware acceleration.

    ### Best Practices for AI-Assisted Android Development

    - Specify the minimum API level in your prompt: "using only APIs available since API 33"
    - Run Android lint (`./gradlew lint`) on all AI-generated code
    - Generate DAOs and repository interfaces first; they have the highest accuracy
    - Never accept AI-generated ProGuard rules or manifest permissions without review
    - Use AI for Compose Preview generation to validate layout before wiring business logic
