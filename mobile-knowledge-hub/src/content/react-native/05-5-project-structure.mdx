    ### Standard Project Structure

    A React Native project generated with `npx react-native init` or `npx create-expo-app` follows a convention that separates native host code from your JavaScript/TypeScript application code. Understanding each directory's role is essential for debugging builds and organising large codebases.

    ```
    MyApp/
    ├── android/           # Android native host (Gradle, Kotlin/Java, NDK)
    │   └── app/src/main/java/com/myapp/   # MainActivity, MainApplication
    ├── ios/               # iOS native host (Xcode, Swift/Obj-C, CocoaPods)
    │   ├── MyApp/         #   AppDelegate.swift, Info.plist
    │   └── Podfile        #   iOS dependency declaration
    │
    ├── src/               # ★ YOUR APPLICATION CODE
    │   ├── App.tsx        #   Root component (NavigationContainer)
    │   ├── screens/       #   Screen-level components (HomeScreen, ProfileScreen)
    │   ├── components/    #   Reusable UI (Button, Card, ProductList)
    │   ├── navigation/    #   React Navigation config + param types
    │   ├── store/         #   Global state (Zustand/Redux stores)
    │   ├── services/      #   API clients, analytics, business logic
    │   ├── hooks/         #   Custom React hooks
    │   └── utils/         #   Helpers, constants, formatters
    │
    ├── __tests__/         # Jest tests (React Native Testing Library)
    ├── package.json       # JS deps, scripts, RN-specific config
    ├── tsconfig.json      # TypeScript config (strict, path aliases)
    ├── babel.config.js    # Babel transforms (JSX, TypeScript, plugins)
    └── metro.config.js    # Metro bundler (resolution, transform, inline requires)
    ```

    The `android/` and `ios/` directories are the **native shell** — each is a full platform project. The `src/` directory is your entire application code. This separation is deliberate: native engineers work in `android/` and `ios/`, React engineers work in `src/`.

    <Callout title="Never Edit ios/ and android/ Manually">
    The native directories are regenerated by `npx react-native init` and `pod install`. Manual edits to `ios/Podfile` or `android/build.gradle` are expected, but never edit auto-generated platform source files (MainActivity, AppDelegate) for configuration. Use `react-native.config.js` for library linking. Manual edits to auto-generated files are lost on `npx react-native upgrade`.
    </Callout>

    ### Feature-Based vs Type-Based Organization

    For small apps (under 20 screens), grouping by **type** (screens/, components/, services/) is simple and discoverable. For large apps (50+ screens), **feature-based** organization scales better because deleting a feature means deleting one folder:

    ```
    src/
    ├── auth/            # Self-contained feature
    │   ├── screens/     #   LoginScreen, SignupScreen
    │   ├── components/  #   AuthForm, OTPInput
    │   ├── api.ts       #   Auth API calls
    │   └── store.ts     #   Auth state (Zustand slice)
    │
    ├── checkout/        # Self-contained feature
    │   ├── screens/     #   CartScreen, PaymentScreen
    │   ├── components/  #   CartItem, PaymentMethodPicker
    │   ├── api.ts
    │   └── store.ts
    │
    └── shared/          # Truly shared code
        ├── components/  #   Button, Card, TextInput
        └── hooks/       #   useAuth, useDebounce
    ```

    Feature A cannot inadvertently import from Feature B's internals because there is no `index.ts` barrel file exposing them — each feature is a module boundary enforced by TypeScript path aliases.

    ### Monorepo Approach

    Large RN codebases (Shopify, Microsoft, Coinbase) use monorepos with Yarn workspaces, Nx, or Turborepo:

    ```
    packages/
    ├── app-mobile/       # RN app entry point
    ├── app-web/          # React web app (shares types, utils)
    ├── shared-ui/        # Cross-platform UI components
    └── shared-types/     # API response types, DTOs
    ```

    The mobile and web apps share types, utilities, and custom hooks. `metro.config.js` uses `watchFolders` to include sibling packages from the monorepo.

    ### Configuration Files Deep Dive

    **tsconfig.json** should enable `strict: true` — null/undefined errors become build-time failures instead of runtime crashes. Path aliases (`@/` → `src/`) avoid deep relative imports:

    ```json
    {
      "compilerOptions": {
        "target": "esnext",
        "module": "commonjs",
        "jsx": "react-native",
        "strict": true,
        "baseUrl": ".",
        "paths": { "@/*": ["src/*"], "@components/*": ["src/components/*"] },
        "skipLibCheck": true,
        "esModuleInterop": true
      },
      "include": ["src/**/*"],
      "exclude": ["node_modules", "android", "ios"]
    }
    ```

    **babel.config.js** uses the RN preset with module resolution aliases:

    ```javascript
    module.exports = {
      presets: ['module:@react-native/babel-preset'],
      plugins: [
        ['module-resolver', { root: ['./src'], alias: { '@': './src' } }],
        'react-native-reanimated/plugin', // must be last in list
      ],
    };
    ```

    **metro.config.js** configures the bundler — platform resolution order, custom transformers, and inline requires:

    ```javascript
    const { getDefaultConfig, mergeConfig } = require('@react-native/metro-config');
    const config = {
      transformer: { hermesParser: true, inlineRequires: true },
      resolver: { sourceExts: ['tsx', 'ts', 'jsx', 'js', 'json'] },
    };
    module.exports = mergeConfig(getDefaultConfig(__dirname), config);
    ```

    ### Asset and Environment Management

    Static images use `require('./assets/icon.png')` (resolved at build time). Remote images use `<Image source={{ uri: '...' }} />`. Vector icons use `react-native-vector-icons` or `@expo/vector-icons`. Custom fonts are linked via `react-native.config.js`:

    ```javascript
    module.exports = { project: { ios: {}, android: {} }, assets: ['./src/assets/fonts/'] };
    ```

    Environment variables (`.env`, `.env.staging`, `.env.production`) are loaded with `react-native-config` or `expo-constants`. Never hardcode API keys or endpoints — use env files that switch per build variant.

    ### Large-Scale App Organisation (Case Study)

    Shopify's RN monorepo (Shop and Point of Sale) organises by **domain module**: each domain (catalogue, cart, payments, orders) is an isolated package with its own navigation, state, API layer, and tests. A shared core package provides theming, a brand design system, and base components. Domain packages communicate through a typed event bus, not direct imports. This lets 100+ engineers work in the same repo with minimal merge conflicts. Microsoft's Outlook mobile RN app follows a similar pattern with feature flags enabling per-team delivery.
